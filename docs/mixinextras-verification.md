### Real Sodium reproduction and resolved investigation

The disposable clone is `build/real-projects/sodium`, tag `mc1.21.1-0.8.13`, commit `dae4167e7d32a7812556a02d8be73cd5aba459c0`, Gradle 9.4.1 and Java 21. Keep all 652 Java sources and both platforms; do not reduce the project to a fixture.

JDT LS 1.60's annotation-processor model query fails when it resolves another project's configuration without its lock ([upstream issue 3807](https://github.com/eclipse-jdtls/eclipse.jdt.ls/issues/3807)). Setting only `org.gradle.tooling.parallel=false` did **not** fix it (`osgi-e2e-20260914-222819608.log`): the exact candidate and edit passed (startup 44,904.9 ms, warm 406.8 ms), but the AP error remained and shutdown timed out. [Gradle 9.4's independent tooling setting](https://docs.gradle.org/9.4.0/release-notes.html#new-property-for-tooling-api-parallelism-control) therefore is not a verified workaround here. Setting `org.gradle.parallel=false` only in the disposable clone removed that error, retaining annotation processing; the successful current run uses this setting. It also disables ordinary parallel project execution. No installed JDT or global Gradle settings were patched.

The same run exposed a generated PowerShell command bug in timeout cleanup: Lua removed the leading newline after the inserted PID, joining it to the next statement. An explicit separator fixes it. `mcdev-nvim/tests/e2e/teardown_test.lua` now exercises the timeout path and runs the generated PowerShell program; it passes (`build/teardown-timeout-test.log`). Real graceful shutdown remains under investigation.

With `org.gradle.parallel=false`, the next JDT session no longer logged the annotation-processor lock error (`osgi-e2e-20260914-223746255.log`). The run still failed: a cached AST fallback reported only `InvocationTargetException`, with `usedJavaProject=false`, and an orphaned Gradle daemon held test shutdown open until the outer deadline. That owned daemon was identified by PID, parent and command and stopped. Root exception/cancellation handling and ownership-preserving teardown are being corrected before another acceptance claim.

The inherited-pipe regression now passes (`osgi-e2e-20260914-230250658.log`). It launches a real Java parent and child with inherited pipes, plus an unrelated Java process. Both graceful parent exit and a parent that ignores shutdown are covered: captured children are reaped, unrelated Java survives, normal exit stays normal, and timeout stays a failure. The test reproduced the previous implementation's false shutdown timeout (`osgi-e2e-20260914-225108521.log`) before the fix. The wrapper snapshots owned process identities before shutdown, waits for actual root exit, then cleans only surviving captured children so Neovim can receive EOF.

The first real-JDT run of the new mixed-handler cases passed every functional assertion (`osgi-e2e-20260914-230758992.log`) but exposed another teardown error: Neovim `SystemObj:wait` processes fast events only, preventing the scheduled LSP shutdown response from sending `exit`. ## Cold-start blocker

The cold `@At` completion took **17,681 ms** end to end on the local fixture, while the extension reported **55 ms** of processing. The fallback returns candidates without loading a project session, but the installed JDT LS waits for its search index before dispatching `workspace/executeCommand` for custom commands.

This wait is in `JDTLanguageServer.executeCommand`, before the delegate handler. Its `INDEX_INDEPENDENT_COMMANDS` set contains five built-in Java commands and is not an extension registration setting. See the [upstream implementation](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/main/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/JDTLanguageServer.java).

The functional cold-start test is not a latency acceptance test. Removing this delay requires an upstream extension mechanism or a transport/architecture change; do not claim it is fixed by the buffer-only completion path or by warm-cache timings.

The implementation in progress reuses the existing jar through a persistent stdio helper for provisional buffer-only completions. The normal JDT request must still complete to include project-specific injection points and specifiers. Blink appends subsequent responses, whereas cmp replaces its list, so enrichment must preserve candidates without duplicating items or publishing a response for an old buffer version. Helper failure must leave the normal JDT path usable.
